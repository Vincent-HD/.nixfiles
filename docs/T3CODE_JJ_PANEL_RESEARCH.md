# Small jj panel in custom T3 Code: research

Researched 2026-10-12. Research only; no panel implementation, source/patch edits, history changes, pushes, or live `~/.t3` writes.

## Conclusion

**Feasible, but a reliable native panel needs server and contract changes as well as renderer changes.** The pinned server has no jj driver or describe/squash RPC. Keep the scope to the selected workspace's working copy, changed files, roughly five ancestors, description editing, whole-revision squash, and operation-specific undo. A dedicated small jj service avoids implementing all of T3's Git workflows or cloning jj-view.

The existing renderer-only packaging can support a terminal-oriented shortcut/prototype, but cannot add typed server operations. Recommendation: retain the pinned Electron shell and native dependencies, build the matching patched server bundle plus renderer, and replace both in the extracted artifact. This is a proposed packaging extension, not something verified by a build.

## Existing T3 support and integration seams

### What exists

1. **VCS scaffolding, not jj operations.** Contracts accept `git`, `jj`, and `unknown`, with capability/freshness/repository identity schemas ([`vcs.ts:4–38`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/vcs.ts#L4-L38)). Discovery probes `jj --version` but declares `implemented: false` ([`SourceControlDiscovery.ts:41–57`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/sourceControl/SourceControlDiscovery.ts#L41-L57)). An installed jj binary alone does not enable support.
2. **Only Git is registered.** `VcsDriverRegistry` registers Git, fails explicit jj selection, and auto-detects through Git only ([`:68–118`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/vcs/VcsDriverRegistry.ts#L68-L118)). Thus a colocated repository can appear as Git; a jj-only workspace has no supported auto-detected driver. `.t3code/vcs.json` can select jj, but cannot create a missing driver ([`VcsProjectConfig.ts:53–75`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/vcs/VcsProjectConfig.ts#L53-L75)). Git workflows explicitly reject non-Git handles ([`GitWorkflowService.ts:187–237`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/git/GitWorkflowService.ts#L187-L237)). Do not repurpose Git commit/push actions as jj squash.
3. **“SourceControl” is mainly forge integration.** Its provider kinds are GitHub/GitLab/Forgejo/Azure/Bitbucket ([`sourceControl.ts:5–19`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/sourceControl.ts#L5-L19)); its repository RPCs concern lookup/clone/publish ([`rpc.ts:1108–1154`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/rpc.ts#L1108-L1154)). Existing VCS RPC names cover refresh, refs, worktrees, pull and init, not jj revision history/describe/squash ([`:411–437`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/rpc.ts#L411-L437)). `VcsDriver.execute` is an internal service method, not a generic renderer command endpoint ([`VcsDriver.ts:56–80`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/vcs/VcsDriver.ts#L56-L80)).
4. **A concrete panel seam exists, without a plugin registry.** Add a singleton `jj` surface to the enumerated kinds/union and persistence validation in [`rightPanelStore.ts:24–96`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/rightPanelStore.ts#L24-L96), its label/icon/add-menu handling in [`RightPanelTabs.tsx`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/components/RightPanelTabs.tsx#L85-L139), and a lazy content branch in [`ChatView.tsx:10963–11004`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/components/ChatView.tsx#L10963-L11004). The same panel content feeds inline and sheet presentations ([`:11927–12028`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/components/ChatView.tsx#L11927-L12028)). These are source-edit seams, not loadable extensions.

### cwd, environment and authorization

**Evidence:** ChatView already chooses thread `worktreePath` ahead of project `workspaceRoot` and sends `environmentId` with the status query ([`:4120–4133`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/components/ChatView.tsx#L4120-L4133), [`:4222–4224`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/web/src/components/ChatView.tsx#L4222-L4224)). `createEnvironmentRpcCommand` checks origin/destination permissions at execution and exposes `permissionAtom` ([`runtime.ts:782–809`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/client-runtime/src/state/runtime.ts#L782-L809)). Guarded VCS mutations require `source-control:write` ([`clientRpcPermissions.ts:23–35`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/clientRpcPermissions.ts#L23-L35)); status reads require `orchestration:read`, while terminal open/write require `terminal:operate` ([`RpcAuthorization.ts:165–181`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/auth/RpcAuthorization.ts#L165-L181)).

**Recommendation:** key queries/drafts by environment + selected cwd + workspace identity; show that cwd in the panel. Run jj on that environment's server, never on the desktop's local filesystem for a remote thread. Resolve the jj workspace root from the selected cwd; do not substitute the shared repository store or main workspace. A Git worktree is not automatically a jj workspace. Distinguish binary missing, no jj workspace, stale workspace, unsupported server and permission denied. Never initialize/convert repositories automatically.

Use guarded commands for describe/squash/undo, add them to the shared scope map, and enforce scopes server-side. Use `orchestration:read` for metadata, `filesystem:read` if adding file-content diffs, and `source-control:write` for explicit rewrites. jj reads can snapshot files, so document that read-scope status follows jj's normal snapshot behavior; a strictly nonmutating read needs cached mode and must be labeled stale. No forge login or push credential is needed for these local operations.

## jj-view: useful patterns, not a component drop-in

**Evidence:** it separates host-independent SCM state, CLI service and VS Code adapters; the extension wires repository management and SCM/custom editor providers ([`extension.ts:21–58`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/vscode/extension.ts#L21-L58)). Its web views use Svelte ([manifest dependencies](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/package.json#L1267-L1304)); T3's panel seam uses React. The SCM model collects current revision, files, conflicts and a bounded mutable-ancestor list, stopping traversal at a merge/immutable boundary ([`scm-model.ts:150–196`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/scm-model.ts#L150-L196), [`:221–269`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/scm-model.ts#L221-L269)).

Its CLI wrapper uses explicit methods, serialized mutations, argument-array execution, forced no-color/no-pagination, and optional cached reads ([`jj-service.ts:299–325`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-service.ts#L299-L325), [`:362–388`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-service.ts#L362-L388), [`:829–840`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-service.ts#L829-L840)). It supplies a no-op external editor. Its squash accepts explicit source/target/message policy, but description revision is optional and undo targets the latest operation ([`:907–952`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-service.ts#L907-L952), [`:990–992`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-service.ts#L990-L992), [`:1166–1181`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-service.ts#L1166-L1181)).

**Recommendation:** borrow the compact SCM layout and typed CLI boundary, implement in T3's own React/Effect architecture. Improve target freshness and operation-specific undo. Omit graph lanes, drag/drop, editable historic diffs, forge integrations, workspace creation and upload commands.

**License evidence:** jj-view is **Apache-2.0**, not MIT ([`LICENSE:1–4`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/LICENSE#L1-L4)). Redistributing copied/modified code requires license inclusion, retained attribution, modification notices, and relevant NOTICE attribution if supplied ([`:90–116`](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/LICENSE#L90-L116)). Recommendation: independently implement the small concept; if copying code/assets, audit their notices and extend the packaged license manifest. The current repack's unchanged manifest would not account for new copied code.

## CLI behavior that constrains the panel

1. **Snapshots and identity.** Most jj commands snapshot changed working-copy files and replace the working-copy commit; separate workspaces have separate working-copy revisions ([pinned `working-copy.md:5–16`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/docs/working-copy.md#L5-L16), [official workspace/staleness explanation](https://docs.jj-vcs.dev/latest/working-copy/#workspaces)). Recommendation: snapshot once, then read one captured operation view for a coherent response; subsequent cached reads use `--ignore-working-copy`/`--at-operation` where supported. Capture full commit IDs, change IDs, parent IDs and operation ID. Display short IDs only. Never send moving `@`, `@-`, or ambiguous abbreviated change IDs as mutation targets.
2. **Bounded structured reads.** Official templates expose JSON serialization, current-workspace/conflict/empty/immutable flags and changed-file lists ([`templates.md:119–121`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/docs/templates.md#L119-L121), [`:269–300`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/docs/templates.md#L269-L300)). Ancestor revsets can be bounded ([`revsets.md:252–268`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/docs/revsets.md#L252-L268)). Recommendation: `log --no-graph --limit 6 -r 'ancestors(<full-wc-id>)' -T <fixed JSON-lines template>`; include parent IDs so a list never implies a false linear chain. Use proper JSON escaping and schema validation, not human log/summary parsing. Older jj versions may need the explicit escaped-template approach used by [jj-view's template builder](https://github.com/brychanrobot/jj-view/blob/f7d9abca3cfa57adf2c0ee7b572ba9ea86fc8e51/src/core/jj-template-builder.ts#L38-L85). Keep file statuses/paths structured; handle rename, unusual names, binary files and truncation explicitly.
3. **Description editor.** `describe` defaults to `@`; `--message` or `--stdin` avoids launching an editor, and jj checks rewritability ([`describe.rs:43–104`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/cli/src/commands/describe.rs#L43-L104)). Stdin gains a final newline; configured trailers may affect persisted text ([`:130–163`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/cli/src/commands/describe.rs#L130-L163)). Recommendation: a multiline draft with Save/Cancel, full description rather than summary, tied to the selected revision; `describe <full-id> --stdin`, followed by rereading canonical text. Saving describes; it does not commit/create a revision. Preserve dirty drafts during refresh, and reject stale saves rather than overwriting external descriptions.
4. **Squash messages and emptied sources.** Full squash normally abandons the emptied source; abandoning the working copy produces a new empty working-copy revision. Both nonempty descriptions may require an editor. `--use-destination-message` discards source descriptions; `--message` supplies the final destination description ([`squash.rs:53–76`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/cli/src/commands/squash.rs#L53-L76), [`:148–180`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/cli/src/commands/squash.rs#L148-L180)). Recommendation: choose an explicit mutable ancestor; execute `squash --from <full-source-id> --into <full-target-id>` with exactly one explicit message policy. Offer “Keep destination description” as default plus “Edit combined description” showing the exact resulting text. Never silently concatenate or rely on an external editor. Refresh IDs, files and drafts after success. Whole revision only initially; omit `--keep-emptied` unless intentionally changing normal semantics.
5. **Immutable/conflicted states.** Immutable heads and their ancestors are configurable; root is always immutable ([`config.md:596–626`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/docs/config.md#L596-L626)). Recommendation: show badges and disable forbidden rewrites; never add `--ignore-immutable`. Conflicts are representable revisions, not universally forbidden operations. Allow description-only edits on mutable conflicted revisions; for the first squash UI conservatively disable conflicted endpoints, explain why, and display any conflicts produced by otherwise valid squashes. Show merge parents and require explicit destination selection; do not guess `@-` at merges. Recheck all states server-side.
6. **Undo and concurrency.** Operation IDs identify repository-wide operations; `op revert <id>` applies the inverse of that specific operation, while latest undo can affect somebody else's action ([official operation log](https://docs.jj-vcs.dev/latest/operation-log/), [`operation/revert.rs:30–65`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/cli/src/commands/operation/revert.rs#L30-L65), [`undo.rs:30–52`](https://github.com/jj-vcs/jj/blob/78dd53c5b67bcf3cff8cb9a9f15dbb9a4e129398/cli/src/commands/undo.rs#L30-L52)). Recommendation: capture pre/post operation IDs and verify which operation belongs to the action; return that ID in the receipt. “Undo this action” runs `op revert <owned-id>`, never unqualified `undo` or automatic `op restore`. If concurrent operations make attribution uncertain, withhold one-click undo and expose diagnostics. Serialize app mutations per shared jj repository, not only per cwd. This cannot lock out external agents/CLI users; state checks reduce races but are not atomic compare-and-swap. Do not claim full IDs alone prevent stale/hidden revisions from being rewritten. Reject stale requests, revalidate visibility/working-copy identity, and report concurrent divergence/errors without automatic retries.

## Minimal proposed integration plan

1. **Service and contracts:** add a dedicated `JjPanelService` using existing [`VcsProcess.run`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/vcs/VcsProcess.ts#L23-L59) (argv, cwd, stdin, timeout, output limits). Add narrow `jj.getPanel`, `jj.describe`, `jj.squash`, `jj.revertOperation` contracts/RPCs and thin handlers in [`ws.ts`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/src/ws.ts#L2847-L2872). Return workspace identity, observed operation, revisions/files, availability and action receipts; mutations take expected state and full IDs. Fixed command allowlist, no generic shell API, no push/fetch/bookmark publishing.
2. **Client state/UI:** implement environment-scoped query/guarded commands in `packages/client-runtime`, small web state glue and `jj-panel.tsx`. Wire the right-panel seams above. Refresh when visible, on focus/workspace changes and after mutation; debounce rather than continuously scan/render. Abort/discard responses for the previous environment/cwd. Advertise an explicit server capability so renderer connected to an unpatched remote server disables the panel gracefully.
3. **Keep jj integration honest:** a dedicated panel can coexist with existing Git support in colocated repositories; it does not provide jj checkpoints, thread worktree creation, branch switching or Git workflow replacement. Do not flip global jj `implemented` to true or register an incomplete full driver. Later full integration would also touch registry detection/cache assumptions, `VcsDriver` checkpoint/file APIs, workflow routing and broadcasters. Avoid offering existing Git mutation controls as equivalent jj actions.
4. **Package both sides:** extend the pinned source build to emit server and client together. The server build bundles workspace/JS dependencies with native exceptions ([`apps/server/vite.config.ts:78–107`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/apps/server/vite.config.ts#L78-L107)); replace the complete generated server outputs, not source `.ts` files or a guessed single bundle chunk. Keep compatible native artifacts and Electron bootstrap. Check the actual release artifact layout before repacking. jj must be available in the destination environment's managed PATH; local Nix installation cannot equip a remote host. No new localhost sidecar UI is needed. Give this panel its own Nix enable/disable option so disabling a jj patch preserves the working usage footer.
5. **Focused acceptance before shipping:** real disposable jj repositories covering nested cwd/two workspaces, Git-only/no-jj, mutable/immutable/root/merge/conflicted revisions, multiline/empty descriptions, both message policies, source abandonment/new working copy, concurrent external describe/new/squash, operation attribution/undo, and unusual paths. Check scope denial against the destination server, old-server capability fallback, refresh/draft retention and packaged local server launch. Test outside live T3 state. This research ran no product tests or builds.

Suggested wire shapes (recommendations, not existing APIs):

- `getPanel({ cwd, ancestorLimit })` → workspace root/name, shared repository identity, jj version/capabilities, operation ID, working-copy full commit/change IDs, revision records with full parent IDs/description/state flags, and changed-file records with truncation information.
- `describe({ cwd, workspaceIdentity, expectedOperationId, revisionCommitId, description })` → action receipt and refreshed panel.
- `squash({ cwd, workspaceIdentity, expectedOperationId, sourceCommitId, destinationCommitId, messagePolicy })`, where `messagePolicy` is a tagged choice between keeping the destination text and an explicit replacement string (including an empty string).
- `revertOperation({ cwd, workspaceIdentity, operationId, expectedOperationId })` → a new receipt; require a verified service-owned action ID, and initially disable the shortcut when intervening operations make its effect uncertain.

`environmentId` belongs to the client routing target, as in existing commands, rather than directing an arbitrary host from inside the payload. Before a rewrite, refresh the workspace snapshot and reject mismatched state; never fall back to `@` when a supplied commit ID is missing. Use normal latest-operation mutation execution, not `--at-operation <old-id>` as a supposed concurrency lock: that flag selects a historical view and can create divergent operations. The [official CLI options](https://docs.jj-vcs.dev/latest/cli-reference/#options) describe historical-view execution and its implied cached-working-copy behavior.

Renderer-only alternative: existing [`terminal.open`/`terminal.write`](https://github.com/pingdotgg/t3code/blob/ec80933ac8cd02fec5c97b342462ccc9567cdb1e/packages/contracts/src/terminal.ts#L40-L69) can drive a visible terminal in the selected environment. It entails PTY/shell parsing and `terminal:operate`, rather than narrow source-control permissions. A static command helper is plausible; a robust hidden terminal protocol would add complexity and still lack native typed jj APIs. A desktop IPC executor or external sidecar also needs backend work and special remote routing. Neither is the recommended minimal native panel.
