## Direct answer

**No: T3 does not currently offer a full “delete thread and all discussion-owned files” or permanent-purge mode.** It does already target some associated local resources for cleanup: linked attachments, terminal histories, scheduled tasks, preview tabs and their per-tab download directories. It also marks active work cancelled and detaches provider sessions. Physical cleanup is asynchronous outbox work ([event/effect transaction](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/orchestration-v2/EventSink.ts#L445-L465)), so accepting the tombstone does not confirm that every file has been removed. `thread.delete` leaves conversation events/projections and other thread-associated artifacts behind.

The UI presents Delete separately from reversible Archive/Unarchive. The typed `thread.delete` API payload only has `commandId` and `threadId`; it has no purge/permanent flag ([command schema](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/packages/contracts/src/orchestrationV2.ts#L2599-L2613), [lifecycle dispatch](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/orchestration-v2/ThreadLifecycleService.ts#L90-L108)). The UI confirmation says it “permanently clears conversation history,” but the persistence path does not erase it ([confirmation](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/web/src/hooks/useThreadActionMenu.ts#L290-L314)).

There is no dedicated per-thread delete command in the CLI thread subcommands (`list`, `start`, `send`, `show`). `t3 project remove --force` is a broader option: it deletes project threads by dispatching the same `thread.delete` lifecycle before removing the project record ([CLI thread commands](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/cli/thread.ts#L499-L710), [CLI project remove](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/cli/project.ts#L504-L540), [project cascade](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/project/ProjectService.ts#L394-L470)). It is not a purge either.

Thread deletion and workspace/worktree deletion are independent. The UI asks separately before removing an otherwise orphaned worktree, or follows a separate automatic-cleanup setting; `thread.delete` itself has no worktree path argument ([worktree choice](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/web/src/hooks/useThreadActions.ts#L438-L484), [delete then optional worktree removal](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/web/src/hooks/useThreadActions.ts#L486-L549)). The worktree is project data, so it should remain outside the default temporary-thread purge.

## Can T3 reuse a scoped recursive cleanup?

There is no current “conversation folder” to recursively remove. A recursive operation over `<stateDir>`, `attachments`, `logs`, browser profiles, provider homes, a worktree, or a project directory would cross ownership boundaries. Flat attachment filenames and provider-log segments use sanitized/truncated thread IDs; inference: those lossy segments are a weaker ownership check than exact IDs and may be ambiguous, so broad globbing is unsafe.

T3 can safely reuse parts of its current cleanup for specifically owned resources: terminal manager history deletion, preview close (which removes the hashed per-tab download directory), and exact attachment unlinking. For newly owned files, add an ownership manifest with resource kind, generated ID, owner thread ID and canonical root. Record browser screenshots and completed recordings against that manifest; associate uploads with a thread when claimed or while still pending. Resolve paths against allowlisted roots, reject symlink/path escapes, and delete only exact owned entries. Use full thread identity or a stable hash, not lossy sanitized names. Never recurse into shared browser profiles, provider homes, caches, worktrees or the project root.

Filesystem cleanup cannot purge conversation content from SQLite. That needs a separate DB purge operation that scrubs events, projections, timeline/tool outputs, and other thread-linked content while retaining only a minimal durable “purged” marker and retry state. Simply deleting projection rows is insufficient: projection rebuild/replay reads the event store, and current compaction deliberately retains creation/deletion anchors. A purge event/marker must prevent old event replay, recovery, snapshots, or new reads from reconstructing the thread. Keep old event payloads out of the marker itself.

Current cleanup effects are durably enqueued alongside event writes and replay-safe cleanup effects are requeued after process loss, which is a good base for retries ([atomic event/effect write](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/orchestration-v2/EventSink.ts#L445-L465), [restart requeue](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/orchestration-v2/EffectOutbox.ts#L496-L525)). But the worker defaults to five attempts and then records failure ([retry limit](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/orchestration-v2/EffectWorker.ts#L590-L595), [terminal failure after limit](https://github.com/pingdotgg/t3code/blob/044f07257c9684ae4543bd1e1ebf9c394e9e3830/apps/server/src/orchestration-v2/EffectWorker.ts#L759-L783)). A purge job should be idempotent per resource, keep explicit pending/failed/completed state, support durable retry/reconciliation beyond a single bounded retry window, and report incomplete purges rather than calling them complete.

## Smallest robust temporary-thread purge design

1. Add an explicit `thread.purge` operation for temporary-thread exit. Keep Archive reversible. Decide separately whether ordinary Delete should eventually call the same operation; do not silently broaden existing Delete semantics. Return completion state rather than claiming a purge as soon as the tombstone is accepted.
2. Atomically mark the thread `purge_requested`, reject new sends/continuations, and enqueue a durable job. Capture exact file IDs, T3 child-thread IDs and thread-scoped event-log segments before removing projections. The marker should retain only thread ID, purge status, time and retry cursor—no title, prompt or transcript.
3. Cancel and await active runs; stop/cancel T3-owned delegated child threads recursively; revoke per-thread MCP credentials; detach/release provider sessions. Close preview tabs, active recordings and terminals. Before deleting a provider event-log segment, drain/close its writer so a late append cannot recreate it.
4. Delete manifest-owned attachments (including pending files attributed to this thread), terminal histories, per-tab download folders, saved screenshots, recording artifacts and exact provider-log segments/rotations. Clear matching web/mobile snapshots and the JJ diff-panel selection on connected clients; invalidate offline copies when they reconnect. Keep shared profiles/caches, provider homes, workspaces and Git checkpoints unless a separate explicit policy owns them.
5. Purge DB conversation events/projections and all associated T3 child-thread content, while retaining the minimal purge ledger/tombstone needed to stop replay, retries and client-cache resurrection. Deliver that minimal marker through reconnect/resync so offline clients can expire cached snapshots. Update event replay, projection rebuild, recovery and snapshot APIs so none can rehydrate purged content. Keep an idempotency receipt or equivalent minimal state so a duplicate command cannot recreate the thread.
6. Expose purge status and retry failed resources durably. Do not promise provider-local or remote deletion unless the provider has a specific supported deletion API and confirms the result. Explain that offline clients are cleaned on next connection, not immediately.

This is **logical/local T3 data removal, not forensic secure erasure**. Unlinking files and deleting SQLite rows do not promise that SQLite WAL/free pages, filesystem snapshots, SSD blocks, backups, synced copies, or provider-retained records are unrecoverable. The product wording should say “purge T3-managed local conversation data” and describe provider/workspace boundaries, not claim secure erase.

## Rough effort and unresolved questions

A core T3-local purge covering the DB/event replay model, ownership manifests, durable job state, existing cleanup reuse, and web/mobile cache invalidation looks like **about 1–2 engineering weeks** including focused path-safety and recovery verification. Provider-local integrations are additional and cannot be estimated until each provider’s supported local delete API and retention contract are known. This estimate excludes project/worktree cleanup and forensic erasure.

Unresolved product/ownership decisions:

1. Should temporary purge recursively include T3-owned `delegate_task` child conversations? Recommended: yes. Do not attempt to erase provider-native child sessions through T3 unless the provider exposes a specific delete API.
2. Are Codex/Claude/Cursor provider-local session files in scope? T3 scans Claude `projects` and Codex `sessions` transcript roots, but does not bind exact provider-owned files into the thread purge or call provider delete APIs. Decide per provider after verifying supported APIs and whether the record is local, remote, or synced.
3. Should checkpoint refs be removed? Recommended: no by default because they reside in the project Git database and can reference source/workspace snapshots; if desired, make this an independent explicit option.
4. Should temporary threads purge only on explicit exit, or expire after a server-side lease/TTL if the client disappears? Existing delete is explicit; automatic expiry would need durable lease ownership and safeguards for active runs.
5. What should the UI promise about other offline devices? Current client code removes its cache when it receives the delete event; the server cannot immediately erase a disconnected device’s local cache or files copied/exported outside T3.
